# 最终产品：模拟器中的一键启动App

最终交付不是一组命令：在独立模拟器中打开「乐跑助手」，准备检查全部满足后，
一次点击开始完成路线、随机逐点打卡、里程和正常结束流程，并用App实际成绩验收。
密码、需要本人完成的验证等必要交互要明确暂停；不得假造认证或有效结果。
2026-10-14用户已明确授权：仅限本项目独立模拟器、用户明确启动且原App三点、
里程及配速满足后，允许正常结束、保存并读取有效成绩。未知状态仍不得提交。

## 2026-10-14 当前接通工作

原生按钮现连接单执行槽、正式入口、因果开始证据、实时卡片路由和有界三轴输入。
只有本机显式提供`launcher-service --runtime .local/launcher/current/runtime.json`才装配
实际执行；缺省仍只检查，不开始。HTTP请求不能提供执行代码、坐标、密钥或修改授权。
重复请求不会排队，独立停止按钮只撤销输入，不等于结束保存。

当前配置是**已确认点的有限试运行**：本机核实五个历史接近位置，但全部候选点、
官方边界和实验连接段未全面核实。未知点暂停，准备报告不应被理解为全场无人值守通过。
三轴链路有独立UID短段接收证据；150秒片段来源另行校验，短段证明不等于当前长段
全量接收、自然步频或目标App步数验收。

本人验证时撤销位置与运动输入、复核正常模式，等待用户正常完成；不点击验证、
不读取摄像头、不提供静态照片代替本人在场。恢复使用新有界输入许可，不重复开始跑步。
授权结束保存须复核当天、暂停页两帧三点、里程及配速，并只发出一次正常确认动作。
保存后还须匹配本次新开始的日期、里程、用时、三点，以及原App有效次数增加一，
否则只报告未确认，不能把“保存”当“有效”。

本轮原生按钮现场预检已通过有限试运行条件，首次启动在原App开始之前被任务栈
解析守卫阻止。Android实际输出`Hist  #0`（多个空格），旧解析只接受单空格；

此前2.20公里记录已在原App显示“跑步记录当天内上传才有效”，不能算本次成功。

## 实现结构

- **安卓原生入口**：`com.edurun.launcher`。展示准备条件、选择本人照片、一键检查并开始。
  不读取QQ/微信认证目录，不收集密码，不将照片传给外部模型；照片保留原文件内容。
- **本机后台**：MuMu官方位置入口在Windows，复用现有Python观察、路网、时钟和驱动核心。
  后台仅监听`127.0.0.1:8766`，模拟器经本实例的ADB反向端口配对，不向局域网开放。
- **独立环境**：每个账号应为独立新建/未登录模板实例，再正常登录；不克隆已登录数据。
  当前实时适配器仍只支持已经核验的项目实例，多账号制作及管理未完成。

## 必须通过的准备条件

1. 本次目标App已完成QQ/微信OAuth授权；安装了QQ/微信或过去登录过不能当作通过。
2. 本人照片确实准备好；文件就绪不等于身份验证成功或所有验证都能无人值守。
3. 区域、道路及全部候选点完成核实，未知点不随意猜测位置。
4. 独立模拟器归属、原始App版本、root关闭和实际uid/SDK正确。
5. 自然运动输入与实时链路经过实际接收及App验收。
6. 当前允许正式跑步，开始/暂停/验证状态明确，运行会话身份可核对。

## 当前已交付到哪一步

原生界面与配对/准备检查接口已编写；原生APK通过本机SDK编译和签名检查。
本机接口检查真实文件/路线及设备守卫，未知登录、运动及完整执行关卡明确标为未就绪。
`/v1/check`和`/v1/start`立即确认后台检查任务（202、checking），客户端只轮询
`/v1/status`取得最终阻止报告；若任务已完成，start直接返回409阻止状态。
**没有自动开始或上传行为**。
这不是最终一键产品验收，不能用界面按钮和测试数量替代MuMu现场完整运行。

用户交还电脑后，已在项目独立MuMu实际安装和打开原生App，核对720×1280布局、滚动、
文件选择和两个检查按钮。后台只监听127.0.0.1，配对配置只写入助手自己的私有目录，
本实例通过ADB反向端口访问；真实原生按钮收到了准备报告。
本人照片通过系统文件选择器选取，助手内保存的文件SHA256与原文件相同；没有进行
本人身份验证、相片编辑或外部上传。条件缺失时「一键检查并开始」实际被阻止，
没有启动新的跑步或提交记录。这只是入口和阻止行为验收，**不是一键跑完整体验收**。
完整实时编排、正常授权状态核验、全部点目录、自然运动/目标步频、自动部署及系统
自启动仍待完成。原始小幅信号及有来源5/10秒跑步片段已实际接收，并核对时钟间断保护
及正常模式恢复，见[传感器实测](sensor-input.md)；不是目标步频或完整流程验收。
前台运动服务已有独立UID消费者实测和两秒许可保护；目前只用于短诊断，
尚未接入本启动按钮的目标App运行流程，也不等于新有效成绩或一键成品。

开发调度链路现用`RuntimeDispatcher`组合`NamedCardObserver`、顺序两帧状态机、
`RoutePlanner`和`MuMuPositionWorker`：未分配时在闭合等待路线上运行；已分配时按名称
转入道路规划；确认打卡后从当前坐标沿道路重新接回等待路线，不跳回起点。
未知点、广告/暂停/本人验证、过期观察或慢速GIS计算均暂停，三点和App里程阈值两帧
确认后只进入待结束状态，不点击上传。
它要求开始动作对应的零状态→新运行两帧`StartWitness`，并绑定设备与当前时效。
本地`StartButtonTemplate`已经按固定布局核对开始按钮像素，历史开始图通过、运行与暂停图
拒绝；模板只留本机，不提交地图或原始截图。它只判断按钮文字/外观，历史开始图的GPS
当时为弱，**不能把模板匹配当作准备条件通过或开始授权**。运行准备关卡仍要求完整
实际文案`GPS信号优`，不接受简写`优`。
**实时开始连接器尚未在App正式会话现场验收、也未接入原生执行入口**，不能把字段
手工填true就视为真实开始；当前启动App不会调用该链路自动开始跑步。组合测试及
历史图解析尚不能替代MuMu实时链路验收。

新增实际登录准备链路：本次从原生助手正常打开4.3.0客户端，关闭唯一已知广告按钮，
切换「我的」并检查唯一可见的ID格式、已登录昵称字段及学生认证文案，再返回助手。
只输出状态，不输出昵称、ID、手机号或头像；不读QQ/乐跑认证目录，不点击跑步。
密码/摄像头/其它认证页不读取或抢回；背景任务顶部为已有MapRun等页面时不覆盖会话。
本次原生按钮报告中的登录项已实际通过并显示，但这是**已登录UI证据**，不是服务端
OAuth的独立证明；真正开始流程仍需重新校验。场地、运动/完整流程不足仍阻止开始。

`StartConnector`现已实现实时MapRun采集、固定像素模板、一次点击及三帧`StartWitness`
的连接算法：动作前再次确认前台/两秒观察时效/显式准备许可，重复请求不会重试，
非正式零状态/弱GPS/本人验证/缺少新计时两帧不允许移动。
它的算法测试已通过，但**还没有在本次App实际调用开始，也没有接入原生按钮执行**；
不能将新增类或合成因果测试说成实时正式开始验收。

登录检查需要暂时切换客户端界面，助手使用singleTask保留请求/忙碌状态；
后台重复检查立即返回checking，不排队再次导航，状态查询不会等待整个检查结束。
冷启动观察窗口为30秒；「我的」点击后继续等待界面数据，不再次点击。
新版原生客户端最多观察60秒，期间只GET状态，不因慢响应或断线重发POST。
连接中断不意味着后台任务已取消，界面会明确提示可能仍在检查。
兼容未重启的旧同步后台；新异步服务部署/现场验证与APK安装分别记录。

4.3.0/code230实际学生资料页还存在不暴露昵称资源ID的布局。该布局只有在标题、
选中标签、正数ID、已认证学生状态及唯一可见头像布局同时匹配时才确认已登录UI；
隐藏或重复昵称字段不能走此回退。不会输出身份字段，也不将UI检查当服务端认证证明。
